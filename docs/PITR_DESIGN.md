# PostgreSQL 连续归档与 PITR 设计

## 1. 状态与目标

本文件是待现场评审、部署和演练的设计，不代表当前环境已经启用 WAL 归档或时间点恢复。现有已实现基线仍是每 6 小时一次的加密 `pg_dump`，未经实测的目标为 RPO 不高于 6 小时、RTO 不高于 2 小时。

仓库提供 `deploy/pitr/verify-readiness.sh` 作为只读上线/巡检门禁，但不提供自制 `archive_command`。脚本支持现场选定的 pgBackRest、WAL-G 或 Barman：先通过独立 `pg_service` 核对 PostgreSQL 16 的 `archive_mode`、`wal_level`、`full_page_writes`、数据校验和、非空归档命令/库和有界 `archive_timeout`，再检查 `pg_stat_archiver` 的最近成功年龄及未恢复失败，最后调用所选工具的只读检查并要求至少一份物理备份。任何数据库、DNS、凭据、对象存储或工具检查失败都会非零退出；配套 systemd timer 五分钟后自动重试，不会把检查失败写成归档成功。

该预检只能证明“当前设置与外部工具可读”，不能证明 WAL 链连续、远端不可变、备份可恢复或 RPO/RTO 达标；这些仍必须通过本文件第 5 节的演练取得证据。

若矿方要求分钟级 RPO，应在独立预生产环境从 pgBackRest、Barman 或 WAL-G 中选定一个归档实现。选型前必须联网固定版本和镜像摘要，复核许可证、CVE、PostgreSQL 16 兼容性、对象锁支持和恢复演练证据；不能在未验证时把工具直接加入生产 Compose。

目标状态：

- PostgreSQL 开启 `archive_mode=on`，已完成 WAL 通过加密通道复制到异地不可变存储。
- 归档端断网时 `archive_command` 返回失败，PostgreSQL 保留 `pg_wal` 并持续重试；不得用返回成功或删除 WAL 的脚本掩盖失败。
- 本地 WAL 使用量、最老未归档 WAL 年龄、最近成功归档时间和归档失败数均有告警。
- 每日至少一份可校验的物理全量备份，WAL 链覆盖两个相邻全量备份之间的全部时段。
- 恢复只写入隔离的新集群，按明确的 UTC `recovery_target_time` 或事务 ID 停止，再执行应用级对账。

## 2. 断网与容量边界

本地 WAL 预留不能用平均写入量估算：

```text
本地 WAL 需求 = 峰值 WAL 字节/秒 × 最大异地断网秒数 × 1.5
```

现场必须测量峰值事件补传、通知写入、审计和批量维护同时发生时的 WAL 速率。数据库卷应为 `pg_wal` 积压设置独立容量告警：50% 提醒、70% 严重、85% 紧急。达到紧急阈值时禁止自动删除未归档 WAL；由容量保护策略限制非关键批处理，并保证事件与审计写入优先级。

归档恢复后应限制上传并发，让实时数据库 I/O、WAL 归档追平和边缘事件补传共存。验收时记录归档积压清零时间以及数据库 P95/P99 延迟，不能只验证文件最终出现。

## 3. 凭据与不可变性

- 数据库主机只持有向指定前缀新增对象所需的最小权限，不得拥有缩短保留期或删除对象锁版本的权限。
- 归档对象必须在客户端加密；加密密钥和对象存储凭据由不同密钥域托管，不进入镜像、Git、命令行或普通日志。
- 传输强制 TLS 并校验服务端证书；对象名包含集群身份和时间线，生产、预生产与演练前缀严格隔离。
- 远端启用合规保留或等价不可变策略。保留周期由监管、事故调查和数据治理共同批准。
- 时间线历史文件、备份清单、校验和及恢复配置与 WAL 一并保护。

## 4. 恢复步骤

1. 创建网络隔离、无生产写入出口的新 PostgreSQL 16 集群，确认目标数据目录为空。
2. 获取目标时刻之前最近一份已验证物理全量备份及连续 WAL，验证清单、签名、对象版本和密文摘要。
3. 恢复全量备份，配置只读归档取回命令和 UTC 恢复目标；先使用 `recovery_target_action=pause`。
4. 启动数据库，确认时间线、恢复目标和最后重放 LSN；不得让演练集群连接通知网关、IdP、摄像头或边缘节点。
5. 在暂停点核对 Alembic revision、核心表行数、事件/审计时间边界、区域权限、模板密钥版本和最近事务。
6. 提升新时间线前保存证据；灾难切换必须经过双人批准、DNS/连接串变更计划和旧主库写入隔离。
7. 启动同版本只读 API 冒烟，记录实际 RPO、RTO、缺失事务范围及所有异常。

## 5. 上线门槛

至少完成以下演练后，才能把分钟级 RPO 标记为已验证：

- 连续运行 72 小时且每个 WAL 都可从备份清单追溯到远端对象。
- 异地网络中断 2 小时后无需人工重启归档器即可续传并清空积压。
- 归档凭据失效、对象存储 5xx、DNS 故障和数据库主机重启均不会造成 WAL 静默丢失。
- 分别恢复到事件创建前、事件创建后、处置提交后和迁移提交后的四个时间点。
- 执行一次时间线分叉后的再次恢复，证明历史文件和后续备份链完整。
- 在目标峰值写入和断网补传流量下测得 RPO/RTO、磁盘余量、归档追平耗时和 API 延迟。

演练证据必须保存工具版本与镜像摘要、配置哈希、备份/WAL 清单、目标与实际 LSN、起止时间、行数对账、应用冒烟结果和整改工单。

预检部署示例（具体工具变量、凭据和 TLS 根证书只放在 `/etc/mineguard/pitr.env`）：

```sh
MINEGUARD_PITR_PGSERVICE=mineguard_pitr_monitor
MINEGUARD_PITR_TOOL=pgbackrest
MINEGUARD_PITR_STANZA=mineguard-prod
MINEGUARD_PITR_MAX_ARCHIVE_AGE_SECONDS=600
```

安装 `mineguard-pitr-readiness.service` 与 `.timer` 前，必须固定所选工具、PostgreSQL client 和 `jq` 的版本/包摘要，并在目标系统执行 `systemd-analyze verify`。监控系统应把 service 任一次失败、连续失败和执行间隔超过两倍周期视为告警；不得仅因为 timer 处于 active 就判定 PITR 健康。
