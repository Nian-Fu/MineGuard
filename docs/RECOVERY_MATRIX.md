# 自动恢复与故障演练矩阵

## 1. 恢复合同

生产验收必须同时证明进程仍在运行、持久数据没有丢失、积压最终清零、实时数据恢复到新的有效状态，以及恢复期间没有重复业务副作用。一次 HTTP 200、容器重新启动或页面重新显示“在线”均不能单独作为恢复成功证据。

下表中的退避上限是代码或部署模板的当前边界，不是已实测 RTO。所有动态证据仍须在目标 PostgreSQL、对象存储、GPU、RTSP、MediaMTX、IdP 和通知网关环境取得。

| 浏览器完全断网 | `offline` 暂停请求；`online` 立即全量刷新、续签媒体会话并恢复登出待办 | refresh Cookie；无秘密登出待办；SSE 游标 | GET/HEAD 单次最多 5 次后由 20 秒轮询继续；SSE 最高 30 秒 | 断网前后授权数据一致，旧会话世代不能复活 | 代码/静态审查 |

## 2. 不自动重放的写操作

浏览器不会自动重放普通 POST/PATCH。服务端可能已经提交而响应在网络中丢失，盲目重放会造成重复审批、重复配置或错误状态迁移。恢复后客户端先执行 GET 全量刷新；边缘事件、通知、备份上传等具备持久幂等键或显式不可变目标的作业才允许自动补传。

注销是受控例外：浏览器先清除内存凭据，再保存不含令牌的单槽待办，随后在网络恢复、页面重开或下次登录前幂等补发。事件快照法律保留也使用受控持久任务：对象存储故障会返回 503，但 worker 会在网络和进程恢复后继续，不要求浏览器重放 PATCH。设置操作先保护对象再标记数据库，解除操作先解除数据库再清理对象标签；这提供自动最终收敛，但仍不得在上线材料中描述为数据库与对象存储之间的原子分布式事务。

## 3. 强制演练顺序

1. 先记录基线队列深度、最新事件、摄像头媒体时间、数据库 LSN、备份时间和对象摘要。
2. 分别注入 DNS 黑洞、TCP reset、超时、HTTP 429/5xx、进程 kill、主机重启和凭据失效；每次只改变一个变量。
3. 故障期间验证内存、文件描述符、SQLite/`pg_wal`/磁盘增长和告警，不得只等待恢复。
4. 恢复网络或服务但不重启应用，证明各循环能自行收敛；随后再执行进程和主机重启矩阵。
5. 对账幂等键、数据库行数、对象引用/摘要/标签、通知次数、SSE 游标和备份制品组。
6. 保存注入时间、首次检测、首次成功、积压清零、实际 RPO/RTO、日志和指标截图；任何人工干预都必须单独记录。

生产候选至少完成 24 小时混合断网稳定性测试；PITR 还必须满足 `PITR_DESIGN.md` 的 72 小时连续归档与隔离恢复门槛。
